# ru-selective-rules

Независимая программа для Linux: собирает доменные правила обхода российских
блокировок и зарубежных геоблокировок. Одна логическая группа `ru-selective`,
два формата: `ru-selective.srs` для sing-box и `ru-selective.dat` для Xray.
Входящих портов нет. Проект не меняет конфигурацию работающего VPN.

## Источники и границы

* Antifilter: полный `https://antifilter.download/list/domains.lst`.
* Re-filter: `1andrevich/Re-filter-lists/main/domains_all.lst`, исходные домены.
* itdoginfo: `Russia/inside-raw.lst` и `Categories/geoblock.lst`.

Последние два файла itdog включают практические зарубежные геоблокировки.
Списки IP, ASN, подсети Cloudflare, CloudFront, AWS и других хостингов не
загружаются. Домены сервисов из исходных списков сохраняются. Поэтому
доменные правила CDN, явно перечисленные авторами, могут присутствовать.

Для plain/RAW списков используется сопоставление домена и его поддоменов.
`full:`/`DOMAIN,` остаются точными доменами; `domain:`/`DOMAIN-SUFFIX,` —
суффиксами; `regexp:` сохраняет регулярное выражение. IDN переводятся в ASCII,
регистр доменов нормализуется. Регулярные выражения проверяют оба движка.
IP и CIDR исключаются; неизвестный синтаксис не угадывается. Число отклонённых
строк отражается в manifest. Более 1% ошибочных строк (минимум 10) блокирует источник.

У itdog и Antifilter на момент проверки не установлена явная лицензия на
распространение данных. Мы этого разрешения не утверждаем. Re-filter содержит
MIT в корне репозитория; полный текст сохранён в THIRD-PARTY-NOTICES.txt.
Это не доказывает права на каждый исходный набор. Собственная программа
выпущена под MIT; данные не перелицензируются. Проверьте условия источников
перед публичным распространением.

## Установка на Linux

Нужны Linux с systemd 249+, Python 3.11+, python3-venv, доступ HTTPS,
`/usr/local/lib/sing-box-vpn/sing-box-stable` и `/usr/local/bin/xray`.
Для полного Antifilter нужен сервер минимум с 2 ГиБ RAM. Служба ограничивает
суммарную память сборщика и дочерних процессов: MemoryMax=1500M,
MemoryHigh=1400M; Go получает GOMEMLIMIT=512MiB и GOGC=25. Это защищает другие
службы при нехватке памяти. Эти параметры не являются измерением успешного
пика на конкретной VM: проверьте первый полный build и повторный build с
принятыми снимками через `systemctl show ru-selective-build -p MemoryPeak`
и журнал службы. На более крупном сервере лимиты можно изменить через
`sudo systemctl edit ru-selective-build.service` в секции `[Service]`.
Python обрабатывает источники последовательно, освобождает принятые списки
после объединения и проверяет DAT потоком без второго списка миллионов правил.
Компилятор sing-box используется установленный; его версия попадает в manifest.
DAT кодируется встроенным кодером protobuf GeoSiteList и обязательно проходит
`xray run -test` с `ext:ru-selective.dat:ru-selective`.

Создайте пустой публичный репозиторий `gam4er/ru-selective-rules`, включите
immutable releases в его настройках **до первого выпуска**. Создайте GitHub
App только для этого репозитория: Contents = Read and write, Metadata = Read.
Не выдавайте другие разрешения и не включайте webhook. Установите App только
в этот репозиторий. App ID и Installation ID не секретны; PEM — секрет.

```sh
sudo bash install.sh APP_ID INSTALLATION_ID /secure/location/app.pem
sudo systemctl start ru-selective-build.service
sudo ru-rules status
journalctl -u ru-selective-build -u ru-selective-publish --since today
```

Установщик не печатает ключ, сохраняет его root:root 0600 вне проекта и
использует systemd LoadCredential. Исходный PEM после установки храните отдельно
в безопасном месте. Не помещайте PEM в Git, аргументы CLI или переменные окружения.
Зависимости издателя закреплены в requirements.txt. Установщик не скачивает
новые версии VPN-движков. Повторная установка сохраняет существующий config.

Конфигурация: `/etc/ru-selective-rules/config.json`. Программа:
`/opt/ru-selective-rules`. Сборщик работает как `ru-rules-build`, издатель —
`ru-rules-publish`. Сборщик не получает ключ. Издатель читает результаты сборки,
но не может их изменить. Токен установки живёт только в памяти процесса,
перевыпускается по истечении часа с запасом 120 секунд, ограничен одним репозиторием.

Таймер запускает сборку каждые шесть часов UTC с задержкой до пяти минут;
успешная сборка через OnSuccess запускает издателя. Persistent догоняет
пропущенный запуск. Никаких периодических запросов к серверу извне нет.

## Команды

```sh
sudo -u ru-rules-build ru-rules build
sudo -u ru-rules-build ru-rules check
sudo systemctl start ru-selective-publish.service
sudo ru-rules status
```

`publish` напрямую требует CREDENTIALS_DIRECTORY от systemd, поэтому используйте
службу. CLI принимает `--config /absolute/config.json` перед именем команды.
`check` проверяет SHA256SUMS, декодирует DAT и SRS, сравнивает нормализованные
правила и проверяет DAT реальным Xray.

Каждый источник имеет отдельный принятый снимок в
`/var/lib/ru-selective-rules/build/sources`. При сетевой ошибке, плохом формате
или падении количества правил больше 30% используется последний принятый
снимок возрастом до 72 часов. Первой успешной загрузки нет или снимок просрочен —
сборка завершается ошибкой, продвижение запрещено. Метаданные сокращения
сохраняются в quarantine; снимок не заменяется. Снижение не принимается
автоматически на следующем запуске. После ручной проверки можно архивировать
конкретный accepted snapshot вне каталога sources и повторить build.

Выходы хранятся в `build/builds/<semantic-sha256>/`; candidate.json указывает
проверенную сборку. SHA256 по отсортированным уникальным типам и значениям
определяет изменение маршрутизации. Время загрузки, порядок строк и дубликаты
нового релиза не создают. Служебный last-check.json показывает свежесть источников
даже при неизменном наборе. Старые сборки не удаляются автоматически.

## Публикация и восстановление

Каждый выпуск получает уникальный UTC-тег с префиксом semantic hash.
Сначала создаётся draft; затем загружаются SRS, DAT, нормализованный JSON,
manifest, SOURCE-NOTICES.txt и SHA256SUMS. Manifest содержит URL, HTTP даты/ETag,
время принятия, hash исходных байтов, количество правил, ошибки, использование
резерва и версии компиляторов. Издатель скачивает каждый asset и проверяет hash,
после чего снимает draft и делает выпуск latest одним запросом. Часть данных
никогда намеренно не публикуется как latest.

`publish/release.json` хранит тег и ID выпуска до загрузки файлов. После потери
ответа на create издатель ищет draft по уникальному тегу; после upload —
перечитывает assets по ID; после publish — проверяет уже опубликованный выпуск.
Повторный запуск безопасен. Несовпадение hash останавливает публикацию,
оставляет draft для расследования; опубликованный immutable выпуск не меняется.
Просроченный источник или неуспешная последняя сборка запрещают продвижение.

### Выбор прежнего выпуска (откат latest)

Неизменяемость запрещает замену файлов и перемещение тега, но GitHub разрешает
менять признак latest уже опубликованного immutable выпуска. Это описано в
[управлении выпусками](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository)
и параметре `make_latest` в
[REST API](https://docs.github.com/en/rest/releases/releases#update-a-release).

Перед откатом остановите таймер и дождитесь завершения текущих build/publish.
Иначе следующая сборка с изменившимися правилами может снова продвинуть новый
выпуск. `systemctl stop` двух oneshot-служб ниже прерывает незавершённый запуск;
его черновик останется доступен для безопасного продолжения.

```sh
sudo systemctl stop ru-selective-build.timer
sudo systemctl stop ru-selective-build.service ru-selective-publish.service
# Замените тег на существующий ранее проверенный выпуск этого репозитория.
TAG=20261028T041853Z-50916ef0c2265b02
sudo systemctl start "ru-selective-select-release@${TAG}.service"
sudo journalctl -u "ru-selective-select-release@${TAG}.service" -n 20 --no-pager
sudo ru-rules status
```

`select-release --tag TAG` использует того же GitHub App через отдельную
службу-шаблон с LoadCredential и общий lock издателя. Тег должен иметь
формат `YYYYMMDDTHHMMSSZ-<16 hex>`: в имени instance он передаётся буквально,
а шаблон использует `%i`, сохраняя дефис. `%I` здесь недопустим: systemd
преобразует дефис в `/` при снятии экранирования.
Допустим только существующий
опубликованный полноценный immutable выпуск настроенного репозитория. До PATCH
проверяются шесть файлов, размеры, GitHub SHA-256 каждого файла, SHA256SUMS,
идентичность manifest/тега, категория DAT `RU-SELECTIVE`, количество и semantic
hash правил DAT. Меняется только `make_latest: true`; файлы, тег, title и notes
не меняются. Затем GET latest должен подтвердить выбранные ID и тег. Подтверждение
сохраняется в `publish/selected-release.json`. Повтор после потерянного ответа
PATCH проверит уже выбранный latest и не создаст выпуск или дубликат загрузки.

Откат не обещает мгновенное обновление уже работающих клиентов: они получат
прежние байты при следующем шестичасовом обновлении. Для немедленного результата
перезапустите клиент/его обновление набора. Исправьте источник или программу и
проверьте новую сборку **до** возобновления таймера. После проверки:

```sh
sudo systemctl start ru-selective-build.service
sudo systemctl start ru-selective-build.timer
```

Первый выпуск сам по себе не даёт предыдущей версии для настоящего отката.
API-тесты проверяют выбор старого выпуска, отказ повреждённым/неполным/чужим
выпускам и потерю ответа, но реальный переход между двумя опубликованными
выпусками следует проверить после появления второй изменившейся сборки;
фиктивный выпуск ради этого не создаётся.

Потребители:

```json
{"type":"remote","tag":"ru-selective","format":"binary","url":"https://github.com/gam4er/ru-selective-rules/releases/latest/download/ru-selective.srs"}
```

В Xray поместите DAT в каталог assets и используйте
`ext:ru-selective.dat:ru-selective`; при имени geosite.dat допустимо
`geosite:ru-selective`. Частота обновления клиентов настраивается отдельно.

## Проверка разработки

```sh
python3 -m unittest discover -s tests -v
```

Тесты проверяют типы правил, исключение IP, инвариант hash, снимки и их срок,
карантин, protobuf и возобновление публикации после неоднозначных ответов.
`tests/live_build.py` — локальная Windows-проверка полного реального списка
с установленными движками из соседнего deployment. Выходы в evidence/live
исключены из Git; никакие секреты и запросы записи GitHub не используются.
